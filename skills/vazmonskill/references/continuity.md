# Resume without losing learning

After permission to maintain project documentation, use docs/learning-progress.md or the existing equivalent.
Keep one concise checkpoint rather than duplicating every chat message.
If file writes are unavailable or declined, provide a copyable checkpoint.
Use optional memory only when its tools and permissions exist.

## Checkpoint fields

- Project identity, objective, repository and current branch.
- Learning mode and experience; record explicit mode changes.
- Current stage and approved artifacts/decisions; who approved them.
- Requirement IDs and acceptance criteria, with links instead of duplicate documents.
- What the learner practiced; concepts that still need explanation.
- Actual checks run, their results and outstanding risks.
- Authorized next unit, unresolved question and operations not authorized.

## Resume contract

Read the checkpoint and relevant artifacts. Verify repository identity and inspect current state.
Distinguish user-approved decisions from model suggestions and stale notes.
Confirm conflicts with the learner; do not repeat kickoff for an unchanged project.
Never treat a checkpoint as permission to deploy, purchase or delete.
Reopen only decisions invalidated by observed changes.

## Separate-chat handoff

Provide the topic, minimal project context, learning mode and exact question.
Ask the study chat to return a concise explanation, one example and unresolved doubts.
On return, ask what remains unclear and continue at the same stage.
Do not assume the other chat has repository access or shared memory.
